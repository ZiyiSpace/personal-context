# AI Skill 使用与内容生产工作流说明

整理日期：2026-07-15

用途：给未来的我和其他 Agent 使用。它不是只服务《我被 Superpowers 的 token 消耗教育了一下》这一篇文章，而是说明我本地这些 Skill、外部参考库和内容工作流应该怎么组合。

## 一句话结论

Skill 的价值不是“让 Agent 永远更自动”，而是把某一类反复出现的判断、流程、验收标准写成可复用约束。

对我来说，最重要的判断是：

```text
任务粒度 -> 选择对应浓度的工程纪律
内容资产 -> 先保留证据、判断和边界
敏感动作 -> 发布、抓取、登录态、上传必须人工确认
```

这次 Superpowers 的教训不是“重型 Skill 不好”，而是“把重型流程设成条件反射会很贵”。以后要把 Skill 当成工具箱，不要当成默认人格。

## 事实与判断分层

这份文档里有三类信息，未来引用时要分清：

| 类型 | 含义 | 例子 | 使用方式 |
| --- | --- | --- | --- |
| 客观事实 | 来自本地已安装 Skill、公开仓库、已有笔记或当前稿件 | `gzh-design` 已安装；当前公开 `yichen-skills` 未找到 `Yichen tutorial writing`；本文有真实 Superpowers 触发经历 | 可以作为上下文，但遇到外部仓库、安装量、许可证、平台规则时要重新核对 |
| 我的策略判断 | 基于我的定位、项目经历、成本敏感度和内容目标做出的取舍 | 暂不安装自动发布；优先 HTML/CSS 生成解释图；Superpowers 不默认常驻 | 未来任务默认遵守，除非我明确改方向 |
| 待验证假设 | 目前看起来值得试，但还没有跑过完整闭环 | `guizang-social-card-skill` 适合做封面/小红书卡；Horizon 可做 14 天信息雷达试验 | 只能作为实验候选，不能直接进入主流程 |

因此，其他 Agent 不能把“我现在不建议装”理解成“这个工具不好”，也不能把“这个工具适合某场景”理解成“现在就应该启用”。

## 我的当前定位

我的自媒体不是泛 AI 资讯号，而是：

> 一个正在用 AI Coding、Agent 工作流和真实项目训练自己的 AI 产品新人，公开记录从学生到 AI 产品/自媒体创作者的成长过程。

因此内容的基本公式是：

```text
信息源信号 + 亲自验证 + 人话解释 + 真实场景 + 个人判断
```

任何 Skill 如果会把这个公式里的“亲自验证”和“个人判断”抹掉，就不能作为主流程使用。

## Skill 的四层分类

### 1. 工程纪律层

负责让 AI Coding 不乱跑。核心问题不是文笔，而是需求、规格、实现、测试、review、归档。

| 工具 | 当前判断 | 适合什么 | 不适合什么 |
| --- | --- | --- | --- |
| Superpowers | 继续保留，但不能默认常驻 | 把 idea 做成能打开、能点、能继续迭代的 Demo；复杂功能；需要 TDD、review、计划的任务 | 闲聊、简单问答、小配置、小修小改 |
| Spec-Kit | 新项目或多人协作时再用 | 从 constitution、spec、plan、tasks 到 implement 的完整规格驱动链路 | 只是探索一个想法，或者一次很小的局部变更 |
| OpenSpec | 适合已有项目里的 change 管理 | proposal、spec delta、design、tasks、archive；让一次变更不散在聊天记录里 | 从 0 到 1 的模糊 idea，或者一次临时实验 |
| mattpocock/skills | 值得学它的“轻量可组合”思想 | grill-me、to-spec、tdd、code-review 这类单点工程动作 | 需要全流程托管、强制流程、统一项目方法论的场景 |

我的使用规则：

```text
一句嗨 / 普通问答 -> 不开工程 Skill
需求没想清 -> 用小的追问 Skill 或让 Agent 先问 3 个关键问题
对话已经聊透 -> 收成 spec
已有项目做一次变更 -> OpenSpec
新项目 / 多人 / 长周期 -> Spec-Kit
要把 idea 认真落成 Demo -> Superpowers
```

## 2. 内容编辑层

负责让文章有观点、有证据、有边界，不变成工具流水账。

| Skill / 方法 | 当前状态 | 用法 | 边界 |
| --- | --- | --- | --- |
| `tech-media-editor` | 本地已安装，应该常用 | 用于 AI Coding、Agent、工具工作流、产品实践类长文的诊断、结构重写和深度检查 | 它不是我的个人文风 Skill，也不会自动拥有我的旧文、口头表达和真实经历 |
| `khazix-writer` | 本地已安装，可参考但谨慎使用 | 适合公众号长文的“好奇、真诚、人话、活人感”方向 | 不要直接用卡兹克风格替代我的声音；更适合学习节奏和选题质检 |
| `wechat-article-writer` | 未安装，只看过 skills.sh 信息 | 4 步流程：搜索资料、撰写文章、生成标题、排版优化；有 3.2K installs | 目前不作为主写作工具。它偏通用公众号流程，我更需要“第一手实践 + 技术判断”的编辑器 |
| 逸尘私有教程写作 Skill | 公开仓库未找到可安装版本 | 学它的流程：总编输入、资料/截图/写作/审稿分工、每次产出沉淀资产 | 不能假设 `Yichen tutorial writing` 已开源；也不能复制其私有工作资产 |

`tech-media-editor` 是现在最适合我的内容主编辑器。它要求每篇文章至少过四个门槛：

```text
机制：这件事为什么会发生
证据：我凭什么这么说
决策：读者看完该怎么选
边界：什么情况下我的判断不成立
```

以后写长文，先不要让 AI “直接写一篇”。先给它：

```text
真实现场：
核心判断：
目标读者：
证据材料：
不能夸大的边界：
希望读者做出的判断：
```

## 3. 视觉生产层

负责把文章里抽象的判断变成可读图。这里要区分“解释图”“封面卡”“公众号正文排版”。

| 工具 / 方向 | 当前判断 | 最适合做什么 | 注意事项 |
| --- | --- | --- | --- |
| `gzh-design` | 本地已安装，公众号排版主力 | 把定稿 Markdown 转为可粘贴公众号的 HTML；适合最后排版 | 只在正文和图片都确定后使用；不负责替我改观点 |
| `guizang-material-illustration` | 已安装，但本次生成方向不满意 | 3D 材质解释图、图表重画、机制图 | 不适合当前这篇 Superpowers 文章的气质；避免金属机器、管道、赛博风 |
| `ian-xiaohei-illustrations` | 未安装，但值得参考 | 16:9 白底手绘正文插图；一个动作、少量中文批注、大留白 | 可学其视觉语言，但不要复制样例构图和 IP；当前更倾向用 HTML/CSS 做可控版本 |
| `guizang-social-card-skill` | 未安装，后续可小试验 | 小红书组图、公众号 21:9+1:1 封面对、HTML -> PNG | AGPL-3.0，不能把修改版闭源再分发；适合封面卡，不是正文写作器 |
| 自己写 HTML/CSS 插图 | 当前最推荐 | 文章内信息图、封面文字卡、可控的解释图 | 随机性最低；适合这次“不要再抽卡生图”的需求 |

视觉原则：

```text
真实证据图 > HTML 信息图 > 风格化正文插图 > AI 氛围图
```

配图必须承担一个任务：

- 证明一个现场：用真实截图。
- 解释一个判断：用 HTML 信息图或小黑式隐喻图。
- 承接平台分发：用封面卡 / 小红书卡片。
- 不能只是“看起来像 AI”。

## 4. 平台自动化层

负责抓取、上传、同步、复盘。这个层最容易踩隐私、风控和账号安全问题，所以现在只看方法，不急着装。

| 类型 | 例子 | 当前判断 |
| --- | --- | --- |
| 热点雷达 | Horizon、Agent-Reach | 可作为以后信息入口实验，但不能替代选题判断 |
| 内容/评论采集 | MediaCrawler、逸尘抓取类 Skill | 暂不安装；只有明确研究问题时才做最小采样 |
| 自动写小红书 | Auto-Redbook-Skills | 暂不安装；它会把写作、视觉和发布绑得太重 |
| 媒体生成聚合 | Generative-Media-Skills | 暂不安装；我现在缺的不是更多模型入口，而是更清楚的视觉 brief |
| 自动发布 | social-auto-upload、X Article uploader | 现在不装；发布动作必须人工确认 |

平台自动化的准入条件：

```text
手动做过至少 3 次
输入输出稳定
每周节省至少 30 分钟
失败不会自动公开、泄露隐私或污染账号
```

## 对“这篇 Superpowers 文章”的具体结论

这篇文章已经定稿，核心不是四个仓库评测，而是：

> 给 Agent 的工程纪律，应该匹配当前任务的粒度。

正文结构已经成立：

```text
一句嗨触发 Superpowers
-> 发现余额变化不合理
-> 回看自己为什么依赖 Superpowers
-> 对比 Superpowers / Spec-Kit / OpenSpec / mattpocock skills
-> 得出按任务粒度选择流程的规则
```

图片策略：

```text
封面：HTML 文字封面
开头：真实截图，证明“轻量输入触发重流程”
正文解释图：HTML/CSS 生成，不再优先 AI 生图
四工具比较：留在正文表格里，不强行画成插图
```

## 以后每篇内容的推荐流程

### 0. 信号进入

只记录五行：

```text
信号：原始链接 / 截图 / 推文
我为什么停下来：反差、结果、问题或新变化
和我有什么关系：项目、学习、实习、产品判断或自媒体实践
最小验证：30 分钟能试什么
暂时不确定：还缺哪条事实
```

### 1. 选题判断

先问：

```text
这条内容读完后，读者要做哪个具体判断或动作？
我能拿出哪一条一手证据？
这是不是我亲自试过、亲自踩过、亲自判断过的事？
```

答不上来就先不写长文。

### 2. 证据包

每篇文章建一个文件夹，至少放：

```text
01-原始信号.md
02-亲自验证.md
03-截图与图片清单.md
04-主张与边界.md
```

### 3. 母稿

用 `tech-media-editor` 或同等规则检查：

```text
机制
证据
决策
边界
```

不要让工具介绍按 README 顺序铺开。多工具对比必须先定同一组横轴：

```text
管的范围
触发条件
留下什么产物
上下文 / token 成本
失败模式
我会怎么用
```

### 4. 视觉

先决定每张图的任务，再决定形式：

```text
证据 -> 截图
规则 -> HTML 信息图
概念隐喻 -> 小黑式插图
平台封面 -> social card / HTML 封面
复杂机制或图表 -> 再考虑 AI 生图
```

### 5. 排版

公众号最后用 `gzh-design`。在此之前不要过早排版，因为排版会让半成品显得“像完成了”。

### 6. 平台改写

一个核心观点拆成多平台：

```text
X：锋利判断 + 现场
小红书：人话解释 + 图文卡
抖音 / 视频号：一个冲突 + 一个过程 + 一个结论
B站：完整过程或系列教程
公众号 / 知乎：证据、机制、取舍和边界
```

### 7. 复盘

发布 48 小时后只记录三件事：

```text
用户反复问了什么？
哪一句被收藏、转发或反驳？
下一篇要补什么证据或例子？
```

## 给未来 Agent 的调用建议

如果用户说“帮我写公众号文章”，不要直接进入 `gzh-design`。先判断文章是否已经定稿。

```text
只有素材 / 想法 -> tech-media-editor 诊断
已有草稿但流水账 -> tech-media-editor 重构
已经定稿 -> gzh-design 排版
需要封面 / 小红书卡 -> HTML/CSS 或 social-card 类工具
需要正文解释图 -> 先做 shot list，再决定 HTML 还是图像生成
需要操作验证 / 截图 -> 浏览器 / computer use，但先列隐私边界
```

如果用户说“装某个 Skill”，先判断风险：

```text
只是写作 / 本地模板 -> 可以评估
要读 Cookie / 登录态 / 私聊 / 本地数据库 -> 先安全审计
要自动发布 / 上传 / 评论 / 私信 -> 必须人工确认，不默认执行
许可证非 MIT / Apache -> 不能默认用于商业化或二次分发
```

如果用户说“这个图不好看”，不要继续换 prompt 抽卡。先回到：

```text
这张图要解释哪句话？
读者看完要记住什么？
这件事能不能用 HTML 稳定画出来？
图内文字是否必须由模型生成？
```

## 当前推荐的本地 Skill 使用顺序

```text
内容判断：tech-media-editor
深度研究：hv-analysis（只在真的需要系统研究时）
工程落地：按任务粒度选择 mattpocock式小技能 / OpenSpec / Spec-Kit / Superpowers
公众号排版：gzh-design
解释图：优先 HTML/CSS；必要时参考 ian-xiaohei 或 guizang-material
小红书 / 封面卡：后续再试 guizang-social-card-skill
平台自动化：现在不进入主流程
```

## 不要做的事

- 不要把所有 Skill 都装上，然后让 Agent 自己决定一切。
- 不要把 Superpowers 设成所有对话的默认反射。
- 不要把外部创作者的文风 Skill 当成自己的风格。
- 不要让自动化工具碰账号发布、Cookie、聊天记录和私密数据库。
- 不要用一张漂亮但无信息量的 AI 图替代真实截图。
- 不要为了“看起来流程完整”而把一个小选题做成重型项目。

## 后续可以沉淀的个人 Skill

等完成 3 篇自己认可的长文后，再考虑做 `ziyi-tutorial-writing`。

它应该来自：

```text
我的完成稿
AI 初稿 -> 我修改后的对照
我反复删掉的表达
我反复补充的证据
我偏好的开头、图文密度和结尾方式
```

它不应该来自：

```text
单篇爆款文章
外部博主口癖
泛公众号写作模板
没有经过我亲自改稿的 AI 初稿
```
